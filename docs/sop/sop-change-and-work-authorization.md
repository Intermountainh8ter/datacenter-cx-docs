# SOP: Change and Work Authorization

> Example SOP. Risk classes, approvers, and lead times are set by the facility owner.

## 1. Document control
Use the block from the [SOP Template](sop-template.md).

## 2. Purpose and scope
No one works on or near critical infrastructure without an approved, scheduled, and communicated authorization. Applies to staff, vendors, and construction teams.

## 3. Risk
Unauthorized or uncoordinated work is a leading cause of outages. Two approved activities that overlap on redundant paths are as dangerous as one unapproved activity.

## 4. Pre-site plan
The requester completes this before submitting, and again before travel:
- [ ] Scope, equipment tags, and date agreed with the facility
- [ ] Procedure drafted (MOP for any state change to critical systems) with a pre-site plan and backout
- [ ] Risk class proposed using the table below
- [ ] Vendor staff names, qualifications, and access requests submitted
- [ ] Approval received in writing before anyone travels

## 5. Safety
Authorization does not replace permits (energized electrical work, hot work, confined space, working at height). Each permit is requested separately.

## 6. Procedure steps

| # | Action | Expected response | Init. |
|---|---|---|---|
| 1 | Requester submits the change request with procedure, pre-site plan, and proposed risk class | Ticket created | |
| 2 | Operations reviews the calendar for conflicts and freeze periods | No conflict, or request rescheduled | |
| 3 | Technical reviewer checks the procedure against current drawings | Comments resolved | |
| 4 | Approver at the level required by the risk class approves | Written approval | |
| 5 | Notifications sent to affected parties within the required lead time | Sent and logged | |
| 6 | On the day: requester checks in, operations confirms conditions and opens the window | Window open, logged | |
| 7 | Work performed under the approved procedure only | Step table completed | |
| 8 | Requester reports completion; operations verifies restoration and closes the window | Window closed, logged | |
| 9 | Ticket closed with actual times, deviations, and lessons | Closed | |

### Example risk classes (set by the owner)

| Class | Description | Typical approval |
|---|---|---|
| Low | No interaction with critical systems | Shift lead |
| Medium | Work on critical systems with redundancy kept | Facility manager |
| High | Redundancy reduced, or a single error could drop load | Facility manager and owner's representative, with vendor review |
| Emergency | Needed now to prevent or recover from an incident | Senior person on duty; reviewed afterward |

## 7. Abnormal conditions
- Scope changes after approval: stop and resubmit.
- Conditions on the day are not as planned (alarm, weather, missing person or part): operations does not open the window.
- Work found without authorization: stop it safely, make the area safe, report.

## 8. Backout procedure

| If stopped at | Do this | End state |
|---|---|---|
| Before the window opens | Cancel or reschedule; notify the same parties | No change |
| During the work | The procedure's own backout applies; operations verifies the as-found state and closes the window | As-found state, ticket marked backed out |
| After a backout | Hold a review before re-approval | Revised procedure |

## 9. Records
Tickets, approvals, notifications, and completed step tables are kept together for the period the owner requires.
